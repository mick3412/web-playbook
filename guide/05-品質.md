## 要做

- [ ] **5.1 無障礙**：WCAG AA：對比、替代文字、鍵盤、標題層級；預設認為有障礙，沒用鍵盤和螢幕閱讀器實際走過主要流程就不算通過
  - 幾種做法：(a) design:accessibility-review 技能；(b) web-design-guidelines 技能
  - 檢查：深色和淺色模式都要量對比（S5-01）
- [ ] **5.2 效能**：量 Core Web Vitals；圖片壓縮與尺寸、字型載入
  - 幾種做法：(a) vercel:performance-optimizer 子 agent
- [ ] **5.3 跨裝置**：實際在手機和桌機的瀏覽器看一次
  - 幾種做法：(a) Playwright CLI 批次截圖
  - 檢查：在真的瀏覽器裡用多種寬度截整頁檢查，不只看手機和桌機（S5-05，待試）
- [ ] **5.4 文案檢查**：錯字、斷行、和核准稿一致
  - 幾種做法：(a) design:ux-copy 技能；(b) 5 段網站檢查提示詞（S41）
  - 檢查：7 種一看就是 AI 做的網頁痕跡，逐項檢查（S5-03）
  - 檢查：做完的網站用 5 段提示詞檢查：層級、AI 感、前 5 秒、設計師檢查、手機（S5-02，待試）
  - 檢查：檢查分三級：底線擋上線、習慣要寫理由才能留、加分不擋（S5-04，待試）
  - 檢查：上線前的通用感關卡：先寫設計契約，看實際成品，只給 PASS 或 HOLD（S5-06，待試）
  - 檢查：品質底線：行長、字級、陰影、動效、各種狀態、瀏覽器預設的地方（S5-07，待試）
  - 檢查：AI 感與品質檢查表：一次看實際畫面，依固定順序走完四段，只給 PASS 或 HOLD（S5-08）

## 用什麼工具

- **Web Design Guidelines（Vercel）**（T-13）：審查介面是否符合規範時
- **unslop**（T-29）：畫面一看就是 AI 做的、要改版或上線前審查視覺時
- **Modern Web Guidance**（T-48）：寫元件、表單、動效或想把舊寫法換成瀏覽器內建功能時。寫介面前用 `npx modern-web-guidance search "<需求>"` 查標準做法（負責人允許後實跑：回傳 10 個相關做法，含無障礙與退路）

**這一步可以試的新工具：**
- Playwright CLI（Microsoft）（T-07，待試）：要批次截圖、查選擇器、錄測試時；複查條件：下一支走到 5.3 跨裝置 的作品
  - 測試方法：何時：要批次截圖或測試｜怎麼做：用它截多寬度整頁｜看什麼：速度、穩定性｜有效＝一個指令完成所有寬度
- Hallmark（T-22，待試）：建新頁、改版既有頁、或只想檢查 AI 感時；複查條件：做下一個網站時
  - 測試方法：何時：建新頁或改版｜怎麼做：用它做一頁或檢查一頁｜看什麼：是否一次問齊素材、多寬度檢查、AI 感｜有效＝產出不用大改
- agency-agents（網站挑 3 個）（T-28，待試）：上線前要獨立審查：通用感、無障礙、受眾模擬；複查條件：有網站要上線時
  - 測試方法：何時：上線前要獨立審查｜怎麼做：把 3 個角色檔放進專案各審一次｜看什麼：找出的問題是否中肯｜有效＝至少一個自己沒發現的問題
- Impeccable（T-34，待試）：要給 agent 一組固定的設計指令（polish、bolder、critique、audit、抓 AI 感）時；複查條件：下一次介面改版時
  - 測試方法：何時：下一次介面改版｜怎麼做：同一個畫面用 Impeccable 和 unslop 各改一次｜看什麼：負責人偏好、修改次數｜有效＝明顯比 unslop 好才留
- agent-browser（Vercel Labs）（T-49，待試）：要讓 agent 實際開頁面、填表單、多寬度截圖檢查時；和 Playwright CLI（T-07）比；複查條件：瀏覽器自動化比較組 W6 測試時
  - 測試方法：何時：桌上試驗｜怎麼做：同一頁用它和 Playwright 各做 320／768／1440 三寬截圖與表單送出｜看什麼：指令數、耗時、截圖是否完整｜有效＝步驟更少且結果一樣
